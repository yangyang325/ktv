# 小程序框架设计文档

## 1. 文档信息

- 日期：2026-04-24
- 项目：K 局微信小程序
- 目标：基于 `PRD.MD` 搭建 `原生微信小程序 + TypeScript` 的可演示、可扩展的 MVP 框架
- 范围：覆盖 `v1 P0` 功能流程，并为 `v1 P1` 提供页面与能力占位

## 2. 设计结论

本次框架采用“页面可演示 + 领域分层”的平衡方案：

- 技术栈使用原生微信小程序 + TypeScript
- 前端先以 mock 数据跑通主流程
- 同步建立云开发/云函数目录骨架
- 页面结构按业务流程拆分，避免超大页面
- 核心业务逻辑抽离为独立领域模块，便于后续从 mock 平滑切换到真实服务

推荐采用领域分层方案，而不是纯页面堆叠方案，原因如下：

- PRD 已明确存在稳定的业务边界，如局、门店、报名、候补、通知
- 后续至少会继续扩展 `移除参与者`、`候补转正通知`、`结算` 等能力
- 先分好边界，可以避免后续在迭代过程中频繁搬迁代码

## 3. 本期目标与边界

### 3.1 本期目标

本次框架搭建完成后，应满足以下目标：

- 小程序可直接启动并浏览主要页面
- 可以演示“发起局 -> 预览接龙文案 -> 发布局”的主流程
- 可以演示“查看局详情 -> 报名 -> 候补 -> 退出”的主流程
- 可以在“我的局”中区分发起、参与、候补、历史四类视图
- mock 数据、类型定义、服务层与云函数骨架已经对齐
- `v1 P1` 页面和通知能力已有占位，不阻碍后续继续开发

### 3.2 本期范围

纳入本次框架的内容：

- `v1 P0` 页面骨架
- `v1 P1` 页面与能力占位
- 本地 mock 数据
- 统一的前端服务层
- 云函数目录骨架
- 领域类型定义

明确不纳入本次框架正式实现的内容：

- 在线支付
- 海报生成
- 首页公开 Feed 的完整产品化能力
- 真实微信订阅消息接入
- `v2` 结算逻辑的正式实现

### 3.3 核心假设

- 当前阶段以“深圳 KTV 组局工具”作为垂直 MVP，不做多城市抽象
- 首页在 `v1` 阶段以演示入口和招募中列表为主，不承担复杂发现推荐
- `P1` 能力只要求路由、结构和扩展位可用，不要求业务逻辑完整
- 当前目录不是 git 仓库，因此本次只落设计文档，不执行 commit

## 4. 总体架构设计

### 4.1 顶层目录

建议项目采用如下顶层结构：

```text
ktv/
├─ miniprogram/
├─ cloudfunctions/
├─ mock/
├─ types/
└─ docs/
```

各目录职责如下：

- `miniprogram/`：微信小程序前端代码，包含页面、分包、组件、服务层与领域模块
- `cloudfunctions/`：云函数骨架，承载后续真实登录、门店、局与报名等服务能力
- `mock/`：本地演示数据与 mock 实现
- `types/`：前后端共用的核心业务类型
- `docs/`：设计文档、后续实施计划及补充说明

### 4.2 前端分层

前端建议按照“页面 + 领域模块 + 服务层”的结构组织：

```text
miniprogram/
├─ app.ts
├─ app.json
├─ app.wxss
├─ pages/
├─ packageCreate/
├─ packageManage/
├─ components/
├─ features/
├─ services/
├─ store/
├─ utils/
├─ constants/
└─ styles/
```

分层职责如下：

- `pages/`：主包页面，承载首页、我的局、个人中心、局详情等高频页面
- `packageCreate/`：发起流程分包
- `packageManage/`：管理与扩展能力分包
- `components/`：跨页面复用的基础组件与业务组件
- `features/`：按领域抽离的业务编排逻辑
- `services/`：数据访问、环境切换、云函数调用封装
- `store/`：轻量全局状态
- `utils/`：时间、金额、校验、文案生成等纯函数工具
- `constants/`：常量、枚举、路由名、筛选配置
- `styles/`：全局主题与样式变量

### 4.3 领域模块划分

建议按以下领域拆分：

- `features/party`：局的创建、发布、列表、详情、状态流转
- `features/venue`：KTV 门店搜索、筛选、手动录入兜底
- `features/entry`：报名、候补、退出、递补
- `features/user`：登录态与用户资料摘要
- `features/notify`：通知能力占位与后续事件接口

该划分既能满足当前 MVP，又为后续扩展留下清晰边界。

## 5. 页面路由与分包设计

### 5.1 路由策略

采用“1 个主包 + 2 个业务分包”的结构：

- 主包承载高频页面与首屏入口
- 发起流程单独分包，减少主包体积
- 管理与扩展能力单独分包，为 `P1` 与 `v2` 预留空间

### 5.2 主包页面

建议保留以下主包页面：

- `pages/home/index`：首页
- `pages/my-parties/index`：我的局
- `pages/profile/index`：我的
- `pages/party-detail/index`：局详情
- `pages/common/webview/index`：协议、说明、活动规则等通用页面占位

其中：

- 首页负责承接可参与局、快捷入口与基础演示信息
- 我的局负责聚合发起、参与、候补、历史四类视图
- 局详情是报名、候补、退出、复制接龙文案、管理入口的汇合点

### 5.3 发起流程分包

建议建立 `packageCreate` 分包，包含：

- `packageCreate/pages/venue-picker/index`：选择 KTV
- `packageCreate/pages/party-form/index`：填写局信息
- `packageCreate/pages/party-preview/index`：预览接龙文案并确认发布

发起流程固定为三步：

1. 选择 KTV
2. 填写局信息
3. 预览接龙文案并发布

该流程不建议压缩进单一页面，以免校验规则、草稿缓存与路由参数耦合过重。

### 5.4 管理与扩展分包

建议建立 `packageManage` 分包，包含：

- `packageManage/pages/party-members/index`：成员管理页
- `packageManage/pages/settlement/index`：结算占位页
- `packageManage/pages/notifications/index`：通知设置占位页

用途如下：

- `party-members` 对齐 `v1 P1` 的移除参与者和成员管理
- `settlement` 为 `v2` 结算功能提前预留路由与结构
- `notifications` 为候补转正通知和后续通知设置提供入口

### 5.5 TabBar 设计

底部导航建议与 PRD 保持一致：

- 首页
- 我的局
- 发起
- 我的

其中“发起”建议采用轻入口页，而不是普通列表页。进入后提供两个动作：

- 选择 KTV 发起新局
- 继续未发布草稿

这样既保留中心主操作入口，也降低用户点击链路。

## 6. 数据模型与服务边界

### 6.1 核心实体

本期统一使用以下一等业务模型：

- `User`
- `Venue`
- `Party`
- `Entry`
- `NotifyEvent`

`Settlement` 与 `PaymentRecord` 在本期保留类型定义和路由占位，但不做正式业务实现。

### 6.2 类型文件建议

建议在 `types/` 下拆分为：

- `types/common.ts`
- `types/user.ts`
- `types/venue.ts`
- `types/party.ts`
- `types/entry.ts`
- `types/notification.ts`
- `types/settlement.ts`

其中：

- `common.ts` 放通用响应结构、分页参数、状态枚举
- `settlement.ts` 先定义未来能力边界，避免 `v2` 再反向调整目录

### 6.3 展示友好字段

为减少页面层自行拼装数据，建议在前端 DTO 或视图模型中提供下列派生字段：

- `confirmedCount`
- `waitlistCount`
- `estimatedPerPerson`
- `hostSummary`
- `venueSummary`
- `progressText`
- `statusText`

页面优先消费展示友好字段，底层实体保留标准业务定义。

### 6.4 Mock 数据组织

建议在 `mock/` 下建立：

- `mock/users.ts`
- `mock/venues.ts`
- `mock/parties.ts`
- `mock/entries.ts`

mock 数据需要覆盖以下典型场景：

- 正在招募中的局
- 即将满员的局
- 已满员且允许候补的局
- 已截止报名的局
- 当前用户为发起人、参与者、候补者的不同视图

### 6.5 服务层接口

建议通过统一服务层对外提供能力，页面不直接关心 mock 与云函数差异。

首批服务方法建议包括：

- `getVenueList`
- `getPartyList`
- `getPartyDetail`
- `createPartyDraft`
- `updatePartyDraft`
- `publishParty`
- `joinParty`
- `joinWaitlist`
- `quitParty`
- `removeEntry`
- `getMyPartyTabs`

所有页面仅依赖服务层返回的数据结构，避免直接访问底层 mock 文件或云函数实现。

### 6.6 数据源切换策略

建议通过 `services/config` 管理运行环境：

- 开发阶段默认使用 `mock`
- 通过统一开关切换到 `cloud`
- 页面与领域模块不感知底层来源

这样可以先完成前端与流程演示，再逐步替换真实云开发实现。

### 6.7 接龙文案生成策略

接龙文案生成应作为纯函数模块独立实现，不直接写在页面中。

输入建议为：

- `Party`
- `Entry[]`
- `HostUser`

输出为完整的接龙文案字符串。

这样处理有三点收益：

- 预览页和复制逻辑复用同一套规则
- 后续如需迁移到云端生成，可保持统一模板
- 单元测试边界清晰，最容易先建立质量保障

## 7. 状态流转设计

### 7.1 局状态

建议将局状态统一定义为：

- `draft`：草稿，未发布
- `recruiting`：招募中
- `full`：已满员
- `closed`：已截止报名
- `cancelled`：已取消
- `finished`：已结束

页面按钮、标签文案与操作权限均应基于该状态集合推导，而不是在页面里分别硬编码。

### 7.2 报名状态

建议将报名状态统一定义为：

- `confirmed`：正式报名
- `waitlist`：候补中
- `quit`：已退出
- `removed`：被发起人移除

该状态将直接影响接龙文案、候补顺序与用户当前可执行操作。

### 7.3 用户视角状态

为简化页面渲染，建议基于局状态和报名状态推导前端用户视角状态：

- 未报名：展示“立即报名”
- 已正式报名：展示“已报名”与“退出报名”
- 已候补：展示“候补中”与“取消候补”
- 已截止或已取消：按钮置灰，并展示原因提示

页面应只消费这些聚合态，不自行拼装复杂判断。

### 7.4 发起流程状态

发起流程的路由状态固定为：

1. 选择 KTV
2. 填写局信息
3. 预览接龙文案
4. 确认发布

建议引入草稿缓存机制，确保用户中途返回或关闭页面后仍可继续编辑。

## 8. 错误处理与降级策略

### 8.1 表单校验

页面层需即时处理以下校验：

- 日期不可早于当前时间
- 日期不可超出 30 天
- 时长必须为合法选项或合法自定义值
- 金额必须在约定范围内
- 人数上限必须在 2 至 50 之间
- 备注长度不可超过上限

### 8.2 服务层错误

服务层建议统一抽象错误码和错误提示，至少覆盖：

- 重复报名
- 局已满员
- 局已截止报名
- 用户未登录
- 报名记录不存在
- 发起人无权限执行管理操作

这样页面只负责展示，不承担业务错误翻译逻辑。

### 8.3 降级要求

即使云函数不可用，也应满足以下最低可用性：

- 首页和我的局可以展示 mock 演示数据
- 发起流程可以完成本地草稿编辑与文案预览
- 接龙文案生成可在本地完成
- 页面出现异常时提供明确提示，而不是白屏

该降级策略与 PRD 中“核心功能故障时仍可引导复制基础文案模板”的要求一致。

## 9. 测试与验收策略

### 9.1 单元测试优先对象

优先为纯函数与规则模块补测试：

- 金额计算
- 时间格式化
- 接龙文案生成
- 局状态转换
- 报名与候补序号推导

### 9.2 页面联调主路径

首轮联调应覆盖以下路径：

1. 发起新局
2. 预览并发布局
3. 查看局详情
4. 正式报名
5. 局满后加入候补
6. 退出报名或取消候补
7. 在我的局中查看对应记录

### 9.3 Mock 验收场景

需要至少准备以下页面态：

- 空列表
- 正常招募中
- 即将满员
- 已满员候补
- 已截止
- 发起人管理视图
- 异常提示态

### 9.4 本期验收标准

本期框架完成后，应以以下标准验收：

- 项目目录清晰，前端、mock、云函数、类型分层明确
- 页面路由和分包已建立
- `v1 P0` 页面骨架可浏览
- 发起与报名主路径可通过 mock 演示
- `v1 P1` 页面和通知能力已有占位
- 数据源切换方案已固定，可从 mock 平滑切到云开发
